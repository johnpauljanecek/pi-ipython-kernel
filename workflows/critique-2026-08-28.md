# Critique: ipyforge-kernel API-update plan

**Date**: 2026-08-28
**Reviewer**: independent / skeptical pass over `workflows/2026-08-28-new-api-update.md`,
`extensions/index.ts`, and `server/main.py`
**Verdict**: Over-scoped, under-tested, introduces at least one regression, and leaves a real
timeout bug unfixed. The kernel-registry idea is good; the surrounding plan needs rework.

---

## What's actually solid (credit first)

- **Step 1 (throw instead of `isError: true`)** is correct and was verified against the bundled
  runtime. Good.
- **Step 9** (overall execution deadline vs per-message poll) is a real bug, real fix.
- **Step 16** (python selection) was genuinely rigorous — actual `uv` commands were run to verify
  each spawn mode instead of guessing. That's the bar the rest of the plan should meet.
- The **named-kernel registry** (steps 17–18) is the right mental model and matches Jupyter
  semantics. It cleanly solves the "which kernel" confusion.

Everything below is where I'd push back.

---

## 1. The biggest one: per-session servers may be the wrong primitive

Half the plan (steps 4, 6, and most of 17) is machinery to manage **per-session FastAPI
servers**: ephemeral ports, `server.json` ownership handshakes, adoption on hot-reload, and
orphan cleanup. But re-read *why*: the only things actually shared and mutable were
`config.kernel_connection_file` (the default) and the `_last_output_full` output cache.

Both of those can be made **explicit per-request** on a *single* shared server:

- every endpoint already takes (or could take) an explicit `connection_file`;
- key the output cache by session id / execution id instead of a global.

That deletes the port management, the handshake, and — critically — the orphan-server problem
the plan is now trying to solve. This solves a shared-*state* bug by duplicating *processes*,
and then writes four more steps to clean up the processes it duplicated. I'd want a very
explicit justification for per-session servers before committing, because they're the source
of most of the remaining complexity.

## 2. Persistent-by-default + no mandatory cleanup = guaranteed orphan growth

Step 2 says `session_shutdown` **never** kills kernels. Step 18 says the only other killers are
explicit `kernel_stop`, crash, and "*future, optional* idle timeout." That's the riskiest
possible combination: persistent by default, no owner, and the one thing that prevents unbounded
accumulation (idle timeout) deferred to "optional."

Every session that calls `kernel_start` leaves a permanent process unless someone remembers
`kernel_stop`. Over a week of use that's a pile of zombies. Pick one:

- make persistence **opt-in** (`kernel_start {persist: true}`) with session-scoped auto-cleanup
  as the default, **or**
- make the idle timeout **mandatory**, not "future/optional."

Right now the plan does neither.

## 3. Deployment: the server's Python env is never provisioned for npm/git installs

The kernel self-provisions (`uv tool run --from ipython --with ipykernel` — uv handles the
env). The server does not: it's spawned as `uv run python server/main.py`, which requires the
project's `.venv` (fastapi, jupyter_client, uvicorn, pyzmq). That `.venv` exists in the local
checkout, but an **npm- or git-installed package has no `.venv`**. So the server spawn is
broken the moment this is distributed — which is the whole point of it being a pi package.

Step 8 moves *state* out of the package dir but never addresses *how the server's
interpreter/deps exist* for a distributed install. Specify it (e.g.
`uv run --with fastapi --with jupyter_client --with pyzmq ...`, or publish the server as a
`uv tool`). This is a deployment blocker, not a nitpick.

## 4. You're introducing an orphan-*server* leak

Step 6 removes `killStaleServer`/`lsof` as "superseded by step 17." But step 17's adoption only
works when the new session's **slug matches** the `session_id` in `server.json`. A fresh pi
session has a fresh session id → fresh slug → it will **never** adopt a server left behind by a
crashed or SIGKILL'd session. And `session_shutdown` is *not* guaranteed to fire (crash,
`kill -9`, reboot). So:

- Old code: ugly `lsof` sweep, but it *did* reclaim stale servers.
- New code: nothing reclaims a dead session's server.

This trades a crude-but-functional cleanup for a permanent leak. There needs to be a reaper
(server self-exits on idle/parent-death, or a startup sweep keyed on liveness, not just slug).

## 5. Bugs the plan misses or contradicts itself on

### a. The HTTP timeout is shorter than the kernel timeout

`REQUEST_TIMEOUT_MS = 10_000`, but `default_timeout_s` is 30 (60 in the actual cfg). A
12-second computation aborts the `fetch` at 10s and the tool errors out *even though the kernel
finishes*. Step 3 makes it `AbortSignal.any([signal, AbortSignal.timeout(10_000)])` — still
10s. So step 3 **preserves** this bug, and step 9's server-side fix is *moot* for any run >10s
because the client gives up first. The fetch timeout must be derived from the tool's
`timeout_s` (+ margin); only control-plane calls should use a short timeout. Steps 3 and 9
must be reconciled, not done independently.

### b. `pi.exec` can't do what step 12 asks

The kernel and server are **long-lived, detached, file-logged** processes. `pi.exec` returns
collected stdout/stderr for short commands — it can't stream a forever process to a log file
with `detached: true`. Step 18 correctly says spawn detached via `execa`, which contradicts
step 12's "replace execa with pi.exec." Reconcile: keep `execa`/`child_process` for
kernel/server spawn; `pi.exec` is only good for one-shot things (maybe the `ps` calls in
`kernel_list`).

### c. `kernel_list` inherits the PID-reuse bug it's supposed to help avoid

Step 10 carefully adds start-time comparison for `kernel_stop` so a recycled PID isn't signaled.
But step 18's `kernel_list` decides "alive" with `process.kill(pid, 0)` **only** — so a
recycled PID makes a *dead* kernel show as *alive* (and prevents pruning). Use the same
liveness check in both.

### d. `kernel_start` name-collision race is unspecified

Two sessions call `kernel_start {name:"data"}` concurrently, or a session starts `"data"` while
another owns it. Both write `~/.ipy/kernels/data/`. Define it: name exists + alive → attach or
error; exists + dead → replace. And registry writes (`meta.json`) need atomic write (temp +
rename) — right now there's no locking/atomicity anywhere.

## 6. Process concerns

- **Scope creep.** The task was "update the extension for the new API." That's steps 1–5
  (+12–13). Steps 16–18 are a **feature project** (python selection, registry, `kernel_list`).
  Bundling a ground-up lifecycle redesign into an API-compat pass is how rewrites regress.
  Ship the API-compat baseline first; do the redesign on top of a known-good state.
- **No migration / back-compat story.** Config keys are renamed (`kernel_connection_file` →
  `default_connect`), `kernel_auto_created`/`kernel_pid` are removed, and tool signatures
  change (8→9 tools, new params). The API literally ships `prepareArguments` for exactly this,
  and the plan doesn't use it. What happens to saved sessions/skills calling the old shapes?
- **No automated tests.** Step 15 is a manual checklist. The behaviors that matter most here —
  two sessions don't interfere, kernel survives session end, `kernel_stop` doesn't kill the
  wrong PID, fetch timeout ≥ kernel timeout — are precisely the ones you can't reliably
  eyeball. They need tests.
- **Entangled ordering.** Step 2's "kill server, never kernel" only makes full sense once step
  18 exists; steps 16–18 depend on 8/11/17. The linear list hides these dependencies. Make the
  build order explicit.

---

## Recommended changes

1. Reconsider whether you need per-session *servers* at all (shared server + explicit
   per-request state is simpler and removes the orphan problem).
2. Make persistence opt-in **or** make idle-timeout mandatory.
3. Specify server env provisioning for distributed installs.
4. Fix the fetch-timeout-vs-kernel-timeout bug (and reconcile steps 3/9).
5. Keep `execa` for detached spawns; drop the `pi.exec`-for-kernel idea.
6. Split it: API-compat first (ship), lifecycle redesign second, with tests.

## Bottom line

The **kernel registry + persistent named kernels** idea is good and should be kept. But the
surrounding plan should be re-scoped (compat first, redesign second), the per-session-server
decision should be re-justified or replaced with explicit per-request state, and the timeout,
provisioning, and PID-liveness issues must be fixed before execution.
